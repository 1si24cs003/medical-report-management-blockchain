1. Introduction & Context

Vulnerabilities in Centralized Healthcare Systems & Proposed Ecosystem

Background

Centralized Database Pitfalls

  • Single Point of Failure: Healthcare databases are prime targets for ransomware attacks, unauthorized eavesdropping, and data wiping.
  • Tamper Susceptibility: Diagnostic reports can be altered or forged without reliable audit trails.
  • Unnecessary Repeated Tests: Scattered records prevent doctors from finding previous test results in emergencies.
  • Redundant Storage: Duplicate uploads clog server storage without cryptographic deduplication.

Proposed Blockchain Solution

  • Hybrid Storage Architecture: Sensitive medical files remain off-chain in AES-256 encrypted form; only SHA-256 fingerprints are anchored on the blockchain.
  • Role-Based Consortium: Multi-stakeholder permissions for Doctors, Patients, Lab Staff, and Consortium Administrators.
  • Three-Module Integration: Hospital, Diagnostic Pathology Lab, and Clinic / Pharmacy nodes.
  • Guaranteed Integrity: Instant anti-forgery detection using QR-coded cryptographic hash matching.

3. Limitations of Existing Works

Analysis of the 13 Fundamental Bottlenecks in Prior Literature

Research Gap

3.1 High Cryptographic Complexity

Complex proxy re-encryption and attribute-based encryption hinder practical hospital deployment.

3.2 Excessive Storage Needs

Attempting to store large diagnostic files (MRIs, CT scans) directly on-chain inflates ledger size.

3.3 Public Ledger Privacy Risks

Immutability prevents data deletion. Sensitive medical data must never be committed to public blocks.

3.4 Difficulty in Access Revocation

Permanent cryptographic keys cannot be revoked once shared without complex re-keying schemes.

3.7 Complex Node Infrastructure

Heavyweight systems (Hyperledger/Ethereum) are difficult for small clinics to configure and maintain.

3.13 Lack of Integrated Model

Prior papers isolate single niches (e.g. only PKI or only IoT). None deliver a unified, workable workflow.

4. Problem Statement & 3 Objectives

Clear Rationale & Design Philosophy of the Proposed System

Objectives

Problem Statement: Existing healthcare architectures rely on vulnerable centralized databases prone to unauthorized tampering and fragmented record access, while proposed blockchain architectures are overly complex, computationally heavy, and fail to separate off-chain storage from cryptographic verification.

Objective 1

Reduce Repeated Diagnostic Tests

Why chosen: When prior reports are scattered across clinics, patients are forced into unnecessary repetitive scans. Rapid chronological retrieval solves this immediately.

Objective 2

Detect Duplicate Reports via SHA-256

Why chosen: SHA-256 cryptographic hashes act as unique file fingerprints. Comparing hashes prior to ledger recording prevents duplicate records and saves hospital storage.

Objective 3

Chronological Medical History Timeline

Why chosen: Fragmented records hinder clinical prognosis. A chronological visual timeline lets doctors review patient diagnostic history in seconds.

6. Key Feature 1: QR Code-Based Anti-Forgery

Instantly verify whether a diagnostic report matches its blockchain-anchored fingerprint

Feature 1 of 3
1

Upload Report

Patient or Lab Staff uploads diagnostic report to Node.js backend.

2

Generate Hash

Backend computes unique cryptographic SHA-256 hash (fingerprint) of the file.

3

Store on Blockchain

The report hash and storage reference are immutably anchored on the ledger.

4

Generate QR

A unique QR code is generated pointing to the report's verification endpoint.

Doctor scans the QR

The backend retrieves the off-chain report reference, recomputes the SHA-256 fingerprint, and compares it against the anchored blockchain block record.

Verification Result

MATCH: The checked file is consistent with the anchored fingerprint.
MISMATCH: The file has been modified or corrupted; alert raised!

Technologies: Node.js + QR Code Library + Permissioned Blockchain + SHA-256 Cryptographic Hash

7. Key Feature 2: Time-Expiring Secure Access Links

Patients can share a report with a doctor for a limited period without creating permanent access

Feature 2 of 3
1

Patient Requests

Patient selects a report and asks the backend to create a temporary sharing link.

2

Backend Creates JWT

Node.js generates a signed JSON Web Token containing access context and expiry time.

3

Doctor Opens Link

Backend verifies JWT signature and checks whether token timestamp is still valid.

4

Automatic Expiry

After configured time (e.g. 1 hour or 2 min demo), expired JWT is permanently rejected.

JWT  →  Report ID + Access Context + Expiry Time

Before Expiry

Valid token → access granted, report decrypted on-the-fly for consultation.

After Expiry

Expired token → HTTP 403 Forbidden, access denied, token signature invalidated.

Technologies: Node.js + JSON Web Tokens (JWT) + Cryptographic Signature Verification

8. Key Feature 3: Smart Keyword Extraction (OCR)

Make medical history searchable while keeping the actual diagnostic report protected

Feature 3 of 3
1

Report Uploaded

Patient or Lab Staff uploads a PDF / image of the diagnostic report.

2

OCR with Tesseract.js

OCR engine reads visible text and converts it into machine-readable text.

3

Extract Keywords

System identifies clinical terms: "Blood Sugar", "Fracture", "HbA1c", "Hemoglobin".

4

Store Tags

Keywords and Report ID are indexed in MongoDB for high-speed search queries.

Example Search Flow

Doctor searches: "Fracture" or "Blood Sugar"
→ Database queries fast tag index without decrypting storage
→ Access control is verified before opening decrypted report.

Core Security Benefit

The searchable index contains only selected clinical metadata tags, while the original diagnostic report remains AES-256 encrypted and protected off-chain.

Technologies: Tesseract.js (OCR) + Node.js + MongoDB / JSON Index + Protected Report Storage
